## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 主题能识别哪些图片格式？ | **不再写死清单**：以"运行环境真正能解码"为准。本机 JDK 22 实测 = **jpg/jpeg、png、bmp、gif、tif/tiff、wbmp**；`.jfif`/`.jpe` 等**按内容**接受（入库时规范成 `.jpg`） |

| 能加"可设置视频"吗？ | **能，但分档**：零依赖只能做 **动图/帧序列**（GIF 逐帧、PNG 帧序列）；要真 MP4 必须引入解码器（§2.3 路线 B/C/D）。**已拍板并实施路线 A（见 §4）** |
| 能有背景音吗？ | **能**。**WAV/AIFF（PCM）零依赖**（`javax.sound.sampled`）——**已实施**（`ThemeAudio`，含音量/静音/循环）；MP3/AAC 需 JLayer/JAAD 或 JavaFX Media（未做） |

## 2. 视频背景（含背景音）可行性判断

### 2.1 一句话结论

**"设置视频 + 背景音"在本项目里能做，但必须选路线**：零依赖方案只能到 **动图（GIF）/帧序列 + WAV 音频**；
要 **MP4/H.264 这类真视频**就必须引入解码器（纯 Java 解码库、JavaFX Media、或外挂 ffmpeg），
三者分别付出"性能/体积/溃散风险"的代价。**绘制侧无瓶颈**（§2.5 实测），瓶颈在**解码与依赖**。

### 2.2 硬约束（已核实）

| 事实 | 影响 |
|---|---|
| **JDK 不含视频解码**：`javax.imageio` 只有静态图（+ GIF 多帧）；音频只有 `javax.sound.sampled` 的 WAV/AIFF/AU（PCM）与 MIDI | 零依赖只能做动图/帧序列 + PCM 背景音；MP4 与 MP3/AAC 都要外部能力 |
| GIF **多帧可纯 JDK 读**（`ImageReader.getNumImages(true)` + 每帧 delay 元数据） | "动图当动态背景"零依赖可行，且立刻能用现有图库 UI 承载 |
| JavaFX Media 官方支持：音频 **MP3 / AIFF(PCM) / WAV(PCM) / MP4-AAC**；视频 **FLV(VP6+MP3) / MP4(H.264/AVC)**，含 volume/mute/balance；Windows 7+ 播 MP4 无需额外软件（见 [Oracle JavaFX Media 文档](https://docs.oracle.com/javafx/2/media/overview.htm)） | 路线 C 的格式/音频能力最强 |
| `JFXPanel` 官方定义为**轻量 Swing 组件**（见 [javafx.embed.swing 21 文档](https://openjfx.io/javadoc/21/javafx.swing/javafx/embed/swing/package-summary.html)） | 理论上可放进 layeredPane 当垫层；但需引入 openjfx 多模块 + 各平台 natives，并把 JavaFX 渲染管线接进 Swing（体积/回归代价最大） |
| 当前 `WindowBackdrop.paintComponent` **每帧从原图重采样**（无缩放缓存） | **动态背景的前置改造**：必须先加"按窗口尺寸的缩放帧缓存"，否则每帧都在做 1080p→窗口的重采样 |
| `BackdropManager` 每窗口一个 `WindowBackdrop`（Session） | 媒体必须**全局单解码器 + 多窗口共享帧**，否则 N 个窗口 N 路解码 |
| 退出路径 `Main.cleanupAndExit → BackdropManager.shutdown()`；`componentHidden` 已有钩子 | 播放/音频必须可停（否则最小化到托盘还在解码、JVM 可能不退出） |

### 2.3 路线对比

| 路线 | 能力 | 依赖/体积 | 风险 | 建议 |
|---|---|---|---|---|
| **A. 零依赖：动图 + 帧序列 + WAV 背景音** | GIF 逐帧动图；PNG/JPG 帧序列（自定帧率）；WAV/AIFF 循环 BGM（音量/静音） | **0**（纯 JDK） | 无 MP4；帧序列占磁盘 | ✅ **建议先做** |
| **B. 纯 Java 解码：JCodec（视频）+ JLayer/JAAD（音频）** | MP4/H.264 真视频 + MP3/AAC 背景音 | jar 体积 +数 MB；许可需核对 | **解码性能是唯一硬门**（必须实测）；需限定规格 | ⚠️ 要 MP4 时再上，先做 30 分钟实测门 |
| **C. JavaFX Media（openjfx）** | MP4/H.264 + AAC/MP3 + 音量，官方支持最好 | openjfx 多模块 + **各平台 natives**（几十 MB） | 与 Swing 的渲染/生命周期整合、分发体积、退出清理 | ⚠️ 能力最好但最重，非必要不选 |
| **D. 外挂 ffmpeg（进程管道送 RGB+PCM）** | 格式最全、性能最好 | 需随包分发或要求用户自备 ffmpeg | 破坏"单 jar 免安装"、杀软误报、许可证、路径依赖 | ❌ 不建议作默认 |

### 2.4 无论选哪条路线都要做的架构改造（同一套）

1. **源抽象**：`ThemeStyle` 由"图片文件"升级为"媒体源 + 播放参数"（静态图 / 动图帧序列 / 视频；循环、帧率、音量、静音）；
2. **缩放缓存**（必做）：`WindowBackdrop` 增加 `(媒体源, 窗口尺寸, 模式, 裁剪) → 缩放帧` 缓存，配合 §2.5 的预缩放；
3. **全局帧源管理器**：单解码器 + 播放时钟 + 多窗口共享当前帧（`BackdropManager` 各 Session 只取帧绘制），窗口隐藏即暂停；
4. **音频通道**：单一 `Clip`/`SourceDataLine` 循环播放，音量可调；主题关闭/窗口全隐藏/退出时 `stop()+close()`；配置键 `theme.g.media|loop|volume|mute`（视频优先于图片）；
5. **数据落盘**：媒体复制入库 `data/themes/media/`（与 `images/` 并列），沿用"引用 id 不引用原路径"与删除清理口径；
6. **预览复用**：独立页预览窗直接取同一帧源（不二次解码），独立预览窗因此同时是"媒体播放预览"；
7. **豁免铁律不变**：输入框/密码窗/悬浮球/JOptionPane 照旧不贴图，音频与贴图范围无关联。

### 2.5 本机实测帧预算（`tools/theme-smoke/AnimBudgetProbe.java`，原样输出）

```
frames=24 source=1280x720 window=900x600
1) 每帧 PNG 解码(磁盘)     平均 4.64 ms/帧  最差 6.54 ms  → 理论上限 215.5 fps
2) 每帧解码+按窗口重采样     平均 8.11 ms/帧  最差 10.59 ms → 理论上限 123.3 fps
3) 预缩放缓存 + 每帧 blit   平均 0.07 ms/帧  最差 0.12 ms  → 理论上限 14809.3 fps
预缩放一次性成本: 平均 3.7 ms/帧（24 帧共 88 ms，单窗口）
```

**读数**：30 fps 的预算是 33.3 ms/帧。即便走"每帧解码+重采样"（最笨路径）也只吃掉 **24%**；
加上缩放缓存后 ≈ **4.7 ms/帧（14%）**。→ **路线 A 的动图/帧序列在 720p 级别毫无压力**；
路线 B 能不能实时，**完全取决于所选纯 Java 视频解码器**——这也正是我建议先做实测门的原因。

### 2.6 建议分期

- **阶段一（建议先做，零依赖）**：GIF 动图 + 帧序列 + WAV 背景音 + 缩放缓存 + 全局帧源 + 音量/静音/循环开关；
  验收：24–30 fps 拖窗不卡、隐藏/退出即停、CPU 占用可接受（有实测脚本）。
- **阶段二（若要 MP4）**：先按 2.5 的工具做解码器实测（同分辨率/帧率下能否稳定 ≤30 ms/帧），
  通过再按路线 B 落地，并限定导入规格（建议 ≤1280×720、≤24 fps、≤15 s 循环 + 导入时预抽帧缓存）。
- **不做**：路线 D 作为默认；路线 C 除非明确接受体积与回归面。

## 5. WebP 打不开：原因与修复（2026-10 追加）

### 5.1 现象与两个真实原因

用户反馈"WebP 图片打不开"。核查日志与配置后确认是**两个原因叠加**：

| # | 原因 | 证据 |
|---|---|---|
| 1 | **JDK 没有 WebP 解码器**；`lib/` 插件目录是空的（**没有随包提供插件**，本会话外网不通：`Invoke-WebRequest`/`curl` 对所有站点均失败，无法下载第三方 jar） | `ImageIO.getImageReadersBySuffix("webp")` = false；`lib/` 只有 README.txt |
| 2 | **主题总开关是关的**（配置里只有 `theme.g.image=<uuid>.webp"` 与别名，**没有 `theme.enabled=true`**） | `data/config.properties` 原样；离线快照时 `主题样式 active=false` |

即：即使换一张能解码的图，**没勾"启用照片背景"也不会贴图**。

### 5.2 采取的修复（不引入任何运行时依赖）

   `ThemeImageIo.ffmpegPath()/ffmpegAvailable()/convertToPng()`；`ThemeStore.importImage` 在**按内容解码失败**时，
   若开关允许且本机有 ffmpeg → 转成 PNG 再入库（临时文件导入后即删，**运行时不需要 ffmpeg**）。
   开关：`theme.media.ffmpeg = auto|off`（默认 auto），路径覆盖 `theme.media.ffmpeg.path`；
   UI 入口：图库 **“格式说明…”** 对话框（含 lib/ 绝对路径、插件扫描结果、ffmpeg 状态与复选框）。
2. **把用户那张 WebP 就地修复**（维护工具 `tools/theme-smoke/ConvertUndecodableImages.java`）：

### 6.2 截断容忍度实测（本次由素材准备过程发现）

用同一张真实图片按不同长度截断，实测 ImageIO 行为（本机 JDK 22）：

| 样本 | 头部嗅探 `looksDecodable` | 整图解码 `isUsableImage` | 结论 |
|---|---|---|---|
| jpg 仅前 **400 B** | true | **false** | 只有文件头 → 解不出图 |
| jpg 前 1000 B / 4000 B | true | **true** | ImageIO **容忍**较深截断，会画出残缺图（灰色/错位） |
| png 前 40 / 120 / 400 / 2000 B | true | **false** | PNG 缺 IDAT 一律解不出 |

**由此修正一处口径**：样式解析（`ThemeStore.buildStyle` / `styleFor`）原来用"头部嗅探"判可用，
会把"仅头部完整"的文件当成 active，出现"设置里显示已启用、窗口却没有背景"的错觉。
现改为**整图解码判定** `isUsableImage(File)`（`imageDimension != null`，结果进尺寸缓存，重复调用不重复解码），
契约变为：**解析是否 active ≡ 整图是否可解码**（冒烟里用 6 个样本逐一验证）。
`looksDecodable` 仅保留给"图库列出/排序"这种廉价判断使用。
